# Windows Brute Force Detection — Sigma Rule

I wrote this Sigma rule to detect a possible brute-force login attempt on Windows. 
The basic idea is pretty simple: first identify failed Windows logons, and then look for repeated failures coming from the same source IP against the same user in a short period of time.

The rule uses Windows Security logs and looks for `EventID: 4625`, which is the eventID generated by default for a failed login attempt in windoes security logs. 
I also exclude machine accounts and a few local/empty source addresses so that the correlation is focused on useful authentication activity.

The first part of the rule is called `windows_failed_logon`. It acts as the base detection i.e finds the failed login attempts.
The second part takes the events matched by that rule and correlates them by groups. In my current version, the same username and source IP must produce **at least 5 failed login attempts within 2 minutes** for the high-severity detection alert to trigger.

## Walking through some sample logs

I wanted to check the logic manually before treating the rule as finished, so I made a few simple sample events.

### Sample 1 — a normal failed login

```text
Time: 10:01:10
EventID: 4625
TargetUserName: alice
IpAddress: 192.168.1.50
```

This matches the first part of the rule because the event ID is `4625`.

The username does not end in `$`, so it is not excluded as a machine account. The source IP is also not `-`, `::1`, or `127.0.0.1`.

So this event becomes a `windows_failed_logon` event.

However, it is only **one** failed login. The correlation rule needs 5 matching events in 2 minutes, so this does **not** generate a brute-force alert by itself.
This could be classified as a false positive if the condition of number of failed login attempts in a time frame was not used.

### Sample 2 — repeated failures from the same source

I then considered several failures like these:

```text
10:01:10  4625  alice  192.168.1.50
10:01:24  4625  alice  192.168.1.50
10:01:41  4625  alice  192.168.1.50
10:02:03  4625  alice  192.168.1.50
10:02:18  4625  alice  192.168.1.50
```

All five events match the base failed-logon rule.

They also have the same:

```text
TargetUserName = alice
IpAddress = 192.168.1.50
```

so they belong to the same correlation group.

The first event occurs at 10:01:10 and the fifth at 10:02:18, which is less than two minutes.

That gives us 5 matching failures within the 2-minute window, so the correlation condition:

```yaml
gte: 5
```

is satisfied.

**Result: the rule should trigger a high-severity alert.**

### Sample 3 — failures split between different IPs

I also checked a case where there are five failures overall, but they are not all coming from the same source:

```text
10:05:10  4625  alice  192.168.1.50
10:05:20  4625  alice  192.168.1.50
10:05:35  4625  alice  192.168.1.50

10:05:40  4625  alice  192.168.1.75
10:05:55  4625  alice  192.168.1.75
```

All five events are failed logons, but the correlation rule groups them by both username and IP.

So the groups are effectively:

```text
alice + 192.168.1.50 → 3 failures
alice + 192.168.1.75 → 2 failures
```

Neither group reaches 5.

**Result: no brute-force alert.**

## What I learned from the test

The important part of this rule is not simply detecting `EventID 4625`. A single failed login is normal and can happen because someone mistyped a password.

The more useful detection comes from looking at the pattern: repeated failures against the same account from the same source in a short period.
(However a attacker spoofing IP address could maybe bypass this rule - for that case we may require very complex rule which is out of scope here)

The manual walkthrough also helped me understand why the `group-by` fields matter. If I only counted all failed logons together, unrelated authentication failures from different users or systems could get mixed into the same alert.

This is still an `experimental` detection, and the rule can produce false positives. For example, a user repeatedly entering the wrong password, an application using an old password, or a misconfigured service could create the same pattern. Those cases would need investigation or further tuning in a real environment and that is where role of a SOC Analyst come in to classify between true and false positives and subsequent tuning and actions.
