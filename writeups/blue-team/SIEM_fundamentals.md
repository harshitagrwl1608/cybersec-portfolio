# SIEM Fundamentals

**Category:** Detection & Monitoring

## Objective
Understand why raw, scattered logs aren't enough on their own, what a
SIEM actually does about that, how logs get into one in the first place,
and how an alert moves from "rule matched" to an actual response
decision — without treating a fired rule as a verdict.

## Tools used
Conceptual/platform-level (SIEM as a category — Splunk, Sentinel, QRadar,
Elastic, etc. all implement this same core pipeline)

## Methodology

### What a SIEM Actually Is
**SIEM (Security Information and Event Management)** — a platform that
collects, centralizes, normalizes, correlates, and analyzes logs/events
from many sources at once. The point is giving a security team one place
to look instead of forty.

### Why You Can't Just Read Logs Individually
Logs get generated constantly, everywhere — endpoints, servers, OSes,
applications, firewalls, routers, web services. Working with them one
source at a time breaks down for a few concrete reasons:

- **Too many sources** — hundreds/thousands of devices producing events;
  checking each one separately means you miss things by volume alone.
- **No centralization** — without a SIEM you're logging into each system
  individually just to search its own logs.
- **Limited context** — one event on its own can look completely
  harmless. It's only suspicious once you see it *alongside* other
  events from a different source.
- **Limited analysis** — past a certain event volume, manual review
  stops being realistic. Important stuff gets buried in noise.
- **Format differences** — every source logs differently, which makes
  comparing/correlating across them a mess without normalization first.

### What a SIEM Actually Fixes
```
Collect logs from all sources
        ↓
Standardize / normalize
        ↓
Correlate events
        ↓
Detect suspicious activity via rules
```
One place to collect, normalize, search, correlate, detect, alert, and
support investigation/response — instead of forty browser tabs open to
forty different log consoles.

### Log Sources — Two Buckets

**Host-centric** — events tied to a specific host/endpoint/server/OS.
Generated when a user accesses a file, a file gets modified,
authentication happens, a process runs.
- Windows → **Event Viewer**
- Linux → `/var/log/`

**Network-centric** — communication/access between networked systems.
Generated by host-to-host communication, users hitting network services,
web activity, connections being allowed/denied. Common examples: SSH,
remote file access, firewalls, routers.

Web server logs specifically tend to live at `/var/log/apache` or
`/var/log/httpd` — exact path depends on OS/server/config.

### Getting Logs Into the SIEM (Ingestion)
A few different mechanisms, not mutually exclusive:

- **Agent/provider** — something sits on the endpoint, collects local
  events, ships them to the SIEM continuously.
  ```
  Endpoint → Agent → SIEM
  ```
- **Syslog** — the standard transport for getting log messages off
  network devices and Unix/Linux boxes into a central logging system.
  ```
  Network/Host → Syslog → SIEM
  ```
- **Manual upload** — dropping log files in directly for one-off
  analysis, investigations, or CTF exercises. Not continuous — this is
  the "I already have the file" path, not live collection.
- **Port/network forwarding** — event data pushed over a designated
  network port to a collector. Exact protocol/port depends on the tech.
- **Real-time collection** — continuous ingestion so the SIEM is working
  with events close to when they actually happened, which is what makes
  timely detection/alerting/response possible in the first place.

**Full pipeline:**
```
Log source → Collection/ingestion → Parsing → Normalization →
Correlation → Analysis → Detection → Alert / Dashboard / Search
```

A SIEM can only ever analyze what it actually receives — missing,
delayed, or badly parsed logs quietly become a visibility gap, not just
an inconvenience.

### Detection Rules → Alerts
A detection rule defines a condition; when incoming events satisfy it,
an alert fires.
```
Incoming events → Detection rule → Condition matched? → Alert (if yes)
```

### What Happens After an Alert Fires — This Is the Part That Matters
An alert is not a verdict. The actual process:

1. **Is it false?** → tune the rule, reduce noise, keep the useful
   detection intact rather than just deleting it.
2. **Is it true?** → examine the actual evidence/logs and surrounding
   context.
3. **Contact the asset owner** — was this expected/authorized activity?
4. **Confirm suspicious activity** → move into containment/response per
   the org's actual IR process — e.g. isolate the host, block the
   suspicious IP.

```
Rule → Alert → Investigation → Validation → Tune OR Respond
```
Not: `Rule → Alert → Block`. Skipping the investigation/validation step
is how you get an org that either misses real incidents or auto-blocks
its own legitimate traffic.

### Worked Example — Windows Event ID 4688
**4688** = a new process was created. A naive rule: alert whenever the
new process name is `whoami`.

**The catch:** `whoami` is a completely legitimate command that just
prints the current user identity. It is **not automatically malicious**
— seeing it once tells you almost nothing by itself. What actually
matters is the surrounding context:
- Parent process (did `whoami` get spawned by a normal shell, or by
  something like a web server process that has no business running it?)
- User running it
- Host
- Full command line
- Timing
- What happened immediately before/after
- Whether this was expected at all

Same event, wildly different meaning depending on that context — which
is exactly the "don't judge one log line in isolation" lesson that shows
up again in the Logs Fundamentals writeup for the 4624/4625 sequence.

### Alert Investigation Checklist
1. What log source generated the alert?
2. Which host is involved?
3. Which user/account is involved?
4. What happened immediately before the event?
5. What happened immediately after it?
6. Is the activity expected?
7. Are there related events from other sources?
8. Is the detection rule too broad?
9. Is there enough evidence to confirm suspicious activity?
10. What response action is actually authorized here?

### Full Detection Rule Lifecycle
```
Create rule → Events arrive → Rule matches → Alert → Investigate
   ↙                                                        ↘
False                                                       True
  ↓                                                           ↓
Tune rule                                                Examine → Confirm → Respond → Review/improve
```

## Detection angle (SOC-relevant)
This entire writeup basically *is* the detection angle — it's the
missing middle layer between "raw logs exist" (see the Logs Fundamentals
writeup) and "an analyst does something about an alert" (see the SOC
Fundamentals writeup). The 4688/`whoami` example specifically ties
straight back to this repo's earlier UFW/Sigma rule work: a naive
signature-only rule (alert on process name X) is exactly the kind of
detection that generates noise without context — the fix in both cases
is the same, correlate against surrounding activity instead of firing on
a single indicator alone.

## Key takeaway
A SIEM's entire value proposition boils down to solving a context
problem — no single log source has enough context to make a real call on
its own, and a SIEM's job is stitching enough sources together that the
`whoami` sitting inside an actual attack chain looks different from the
`whoami` a sysadmin ran out of curiosity. The rule firing is the easy
part; the investigation discipline (context → asset owner → confirm →
respond) is where false positives get filtered from real incidents.
